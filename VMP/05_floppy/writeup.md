# Flare-On 5 #12 suspicious_floppy：逐層拆掉 x86 → Subleq → RSSB 三層虛擬機

## 本次成果

這題把密碼檢查藏在三層之下：一段攔截 `INT 13h` 的 16 位元 x86 程式，跑一台 Subleq 虛擬機；Subleq 上再跑一台 RSSB 虛擬機；RSSB 程式才是真正的密碼檢查。本單元一層一層把它們換成更高階的模型，每換一層都和下一層逐步比對，最後把檢查還原成一條公式，再窮舉求出**所有**解：

| 層 | 模型 | 和下一層的比對 |
|---|---|---|
| x86（TMP.DAT） | 常數全部從指令的 bytes 解析 | — |
| Subleq | 16 位元 word，64 KiB 段內繞回 | Unicorn 跑真實 x86：整個段的記憶體、印出的 201 個字元、回傳值全部相同 |
| RSSB | 6 條規則 | lockstep：每執行一條 RSSB 指令，整塊 9,655 個 word 都和 Subleq 相同（最多 504,033 條） |
| 公式 | `y_i = (x_i ^ 33i) + K(p) + sum(c[:p])` | 108 組密碼，每一對的值和最終判定都相同 |

求解結果：

```
Av0cad0_Love_2018@flare-on.com
Av0cad0_Love_2018@flare-on.com?      ? = 任意可印字元
Av0cad0_Love_2018@flare-on.com??
```

第一個就是 flag。後兩種是這次研究的新發現：檢查程式只讀前 30 個字元，也不檢查長度，所以在 flag 後面多接 1 到 2 個字元也會通過。這一點用真實的 x86 程式碼確認過，例如 `…flare-on.comXY` 回傳 `ax=1`，畫面印出「Password Matched」。

研究過程中還找到 RSSB 編譯器的一個 bug：它的「搬移」指令搬不動 `0x8000`。這會讓 `'@'` 剛好在第 16 個字元時，檢查用的常數算錯（見第 4 節）。

## 來源與執行

- 題目映像：repo 內的 `FlareOn/Fo5/12/suspicious_floppy_v1.0.img`（Git 忽略），SHA-256 `cf695438…abf98b`；從中取出的 `TMP.DAT` 也用 SHA-256 固定。
- 實測環境：Windows 11、Python 3.11.9、`unicorn==2.1.1`、WinLibs GCC 16.2.0（編譯 `vm.c`）。
- 不需要 DOSBox 或 QEMU，也不需要已知的 flag：求解只用到程式裡的那張表。

```powershell
VMP/.venv/Scripts/python VMP/05_floppy/devirt.py        # 四道關卡，約 1 分 40 秒，報告寫到 generated/report.txt
cd VMP/05_floppy; ../.venv/Scripts/python -m unittest test_devirt -v
```

`vm.c` 是 Subleq 的 C 版本。Python 跑一次完整檢查要 1.5 億步、約 3.5 分鐘，C 版本 0.9 秒。Python 版的 `Subleq` 類別保留作為可讀的參考，測試會確認兩者前 20 萬步的整個記憶體段完全相同。

## 做法

### 1. x86：攔截磁碟讀寫

`TMP.DAT` 開頭的安裝程式，先把 BIOS 記憶體大小（`0x413`）減掉 32 KiB，把 `TMP.DAT[0x43:0x43+0x5eb0]` 複製到那塊空出來的高位記憶體，再把 `INT 13h` 指向自己。常駐程式只攔截兩種存取：

| `INT 13h` | 磁區（CHS） | 動作 |
|---|---|---|
| 寫入（`ah=3`） | `cx=0x2110, dh=1` | 把緩衝區前 0x40 bytes（密碼）抄到 `cs:0x5e70` |
| 讀取（`ah=2`） | `cx=0x2111, dh=1` | 呼叫 `0x1da` 檢查密碼；通過的話，把讀到的內容換成 `BE SURE TO DRINK YOUR OVALTINE` |

所以 flag 就是密碼本身。`0x1da` 把密碼逐字元展開成 16 位元 word，最多 32 個，遇到 NUL 就停，放在 `0x142b`；接著 `call 0x5d7d`，而 `call` 後面緊接的資料（從 `0x223` 開始）就是 VM 的記憶體。`parse_resident()` 從指令本身讀出這些常數，例如 `add ax, 0x1240`、`cmp ax, 0x20`、`push 5`、`push 0x2dad`、`add bx, 0x123e`。如果 bytes 不是預期的樣子，就直接報錯，不會默默算錯。

這一節的 `INT 13h` 流程是從反組譯讀出來的。實際執行的只有 `0x1da` 檢查函式本身，INFOHELP 和 DOS 都沒有模擬。

### 2. Subleq

`0x5dd9` 是標準的 Subleq：

- 每條指令有三個 word `a, b, c`，執行 `mem[b] -= mem[a]`。若 `c != 0` 且結果 ≤ 0（有號），就跳到 `c`；`c == -1` 停機；否則 `pc += 3`。
- 每一步之後，若 `mem[4] != 0`，就用 `INT 10h` 印出 `mem[2]`，再把兩格清 0。

有一個細節：位址是 `mem0 + 2·i`，在 64 KiB 段內繞回。`mem[-1]` 實際讀到的是 `call` 指令的位移量 `0x5b5a`。所以模型以整個 64 KiB 段為單位，不是一個 Python list。我一開始還把密碼的 word 位置算成 `0x604`，正確是 `(0x142b - 0x223)/2 = 0x904`。改成照 x86 的實際算法寫入位元組之後，這種錯誤就不會再發生。

**Gate 1**：Unicorn 以 16 位元真實模式直接執行 `0x1da`，呼叫者的堆疊放在另一個段。結束後比對整個常駐段（只排除 x86 自己的密碼緩衝區），以及印出的文字和 `ax`：

| 密碼 | Subleq 步數 | 結果 |
|---|---|---|
| （空） | 31,268,700 | 相同 |
| `hello@flare-on.com` | 153,809,631 | 相同 |
| `no-at-sign` | 34,651,986 | 相同 |
| `Av0cad0_Love_2018@flare-on.co` | 155,012,578 | 相同 |

### 3. RSSB：從快照差異找出暫存器

統計 Subleq 的 pc 發現，執行過的程式碼只在 `0x5–0x7eb`；後面約 1 萬個 word 只被當成資料，那就是 RSSB 程式。`0x42a` 每執行一條 RSSB 指令就經過一次，所以在每次經過時拍快照、比較前後差異：`mem[0x7f6]` 每輪加 1、偶爾加 2，正好符合「借位就跳過下一條」，所以它是 IP；`mem[0x7f7]` 是 ACC。以 `0x7f6` 為基底，RSSB 的規則是：

| `x` | 意義 |
|---|---|
| 一般 | `acc = m[x] - acc; m[x] = acc`；IP 加 1，結果為負再加 1 |
| `0` | IP，寫入它就是跳躍 |
| `2` | 常數 0，寫入被丟棄（ACC 照樣更新） |
| `4` / `6` | 輸出字元／輸出旗標：`m[6] != 0` 就印出 `m[4]`，兩格清 0 |
| `-1` | NOP |
| `-2` | 停機 |

這張表是用 lockstep 一條一條補出來的：先只寫最基本的規則，逐步對照，哪一步不一致就補上對應的規則。第 1 步就發現 `m[2]` 寫不進去（常數 0），第 723 步發現輸出旗標。Subleq 的啟動程式只做了一件事：把 IP 從 `0x15b` 設成 `0x15c`。

**Gate 2**（`vm.c lockstep`）：RSSB 模型**從原始映像**獨立開始執行，不是從 Subleq 的狀態複製過來。每當 Subleq 走到 `0x42a`，模型就執行一條指令，然後比對整塊 RSSB 區域；最後兩邊也必須在同一處停機。上表 4 組密碼分別是 101,970、500,076、112,984、504,033 條 RSSB 指令，全部一致。

### 4. 還原檢查公式

RSSB 程式是編譯器產生的，大量改寫自己的運算元來做指標存取，直接靜態反編譯很難讀，所以改用動態方法：

1. **差分執行**：一次只改一個字元，找出執行軌跡的第一個分岔點。改到 `'@'` 時，分岔點在 `0xd1e`（一個尋找 `'@'` 的迴圈）。其他字元則**兩兩成對**被處理，每對相隔約 2.45 萬步，而且改錯某個字元之後，後面的字元仍然照常處理。
2. **找主迴圈**：`0x1364` 剛好被執行 16 次（15 輪加上離開時的判斷）。在每次經過時拍快照，可以看到 `[0xb4e]` 是索引 i，`[0xb40]` 是 `x_i = (c[2i+1]-32)·128 + (c[2i]-32)`，以及指向 `0xa79 + i` 的表格指標。
3. **找比較值**：在每一輪寫入的所有值中，只有 `0x1ffa` 寫進 `[0xb5c]` 的 `y_i` 滿足「`y_i - (x_i ^ 33i)` 在 15 輪都相同」。這個差值就是全域值 G，`y_i` 接著和 `table[i]` 比較。
4. **量出 G**：每個字元各加 1 → `'@'` 之前的字元讓 G 加 1，之後的不影響。把 `'@'` 放在 0 到 31 的每個位置 → `K = G - sum` 只和位置 p 有關，而且是 `0xc00·p`，**唯一的例外是 `K(16) = 0x4000`**（照公式應該是 `0xc000`）。

這個例外的原因是：K 用倍增算出 `(p<<11) + (p<<10)`，而編譯器的「搬移」寫法是先 `acc = -src`，靠「結果為負就跳過下一條」處理正負號，再 `dst -= acc`。`0x8000` 取負之後還是 `0x8000`，所以寫回那一步被跳過，目的格停在 0。p = 16 時 `p<<11` 剛好是 `0x8000`。這個 bug 也寫進了模型（`at_weight()`）。Gate 3 另外構造了 30 組讓某個 `y_i` 等於 `0x7fff`、`0x8000` 或 `0x8001` 的密碼（`boundary_cases()`），結果都和模型一致，所以在目前的測試範圍內，這個 bug 只影響 K。

最後得到的檢查：

```
p   = 第一個 '@' 的位置（沒有 '@' 就直接拒絕，主迴圈一輪都不跑）
K   = (p<<11，若為 0x8000 則為 0) + (p<<10)
G   = K + sum(c[0..p-1])
x_i = (c[2i+1]-32)·128 + (c[2i]-32)              （NUL 之後的格子是 0）
通過 ⇔ 對 i = 0..14 都有 ((x_i ^ 33i) + G) mod 2^16 == table[i]
table = fc7f f30f f361 f151 f886 f3d1 db57 d9d5 e26e f8cd f969 d90c f821 f181 f85f
```

**Gate 3**：共 108 組密碼：

- 邊界情況：空字串、只有 `'@'`、沒有 `'@'`、兩個 `'@'`、超過 32 字元，以及 `'@'` 落在 0 到 29 每個位置各一組。
- 40 組隨機密碼。
- 30 組讓 `y_i` 落在 `0x8000` 附近的構造密碼。

每一對的 `y_i` 和最終判定都必須和 RSSB 模型相同。

**走過的彎路**：我一開始試過不理解語意、直接暴力找答案：對每一對窮舉 95×95 種組合，挑出「執行過的 IP 集合」和其他組合都不同的那一個，假設它就是相等比較成立的那一條路。結果每一對都冒出好幾個這樣的組合，多半是算術上的邊界情況；再加上 G 讓各對互相牽動，迭代在兩個錯誤答案之間來回震盪，沒有收斂。最後還是得先把 G 找出來。

### 5. 求解

不需要 SMT。G 只有 65,536 種可能，給定 G 之後，每一對的 `x_i = (table[i] - G) ^ 33i` 就確定了。兩個字元都是可印字元時，`x_i < 12,288`，可以唯一拆成兩個字元。`solve()` 對每個 G 和每種長度（1 到 32），分三種情況處理每一對：兩個字元都在字串內；第二個是結尾的 NUL；兩個都在字串之後。最後檢查第一個 `'@'` 的位置和 G 是否自洽。第 30、31 個字元不在任何一對裡，只有當它是第一個 `'@'` 或在 `'@'` 之前時才有約束，其他情況就是自由字元 `?`。

**Gate 4**：每一種解都丟回 RSSB 模型（結果必須是 1），也丟到真實的 x86（`ax=1` 且印出「Password Matched」）。另外把每一種解的第 0、13、29 個字元分別改掉，x86 都必須拒絕。

## 測試

`test_devirt.py` 有 14 個測試，約 15 秒。其中 6 個確認錯誤的東西會被擋下：

- x86 指令的 bytes 和預期不同，`parse_resident()` 會拒絕。
- RSSB 少了「常數 0」規則，lockstep 在格子 `0x2` 抓到差異。
- RSSB 少了輸出規則，lockstep 抓到差異。
- RSSB 的起始 IP 用錯（`0x15b`），C 版 lockstep 失敗。
- 拿天真的 `K = 0xc00·p` 公式來預測 p = 16 的 G，和觀測值不符。
- 求解器所用的表被改掉一格之後，就找不到 flag。

其餘測試涵蓋：常數解析、Python 和 C 兩個 Subleq 的整段記憶體一致、RSSB 規則在前 800 條指令都對、沒有 `'@'` 時主迴圈一輪都不跑、flag 被接受而改一個字就被拒絕、求解器恰好找到 3 種解，以及真實 x86 接受 `flag + "!?"`、拒絕少一個字元的密碼。

撰寫測試時我自己也犯了一個錯：輔助函式寫成 `return m.result, m.run(...)`，Python 會先讀 `m.result`，那時程式還沒跑，所以永遠是 0。這讓「沒有 `'@'` 就拒絕」那個測試**因為 bug 而通過**，直到 flag 的測試失敗才被發現。修正之後兩個測試都重新驗證過。

## 限制

- **只模擬了檢查函式**：INFOHELP、DOS 和 `INT 13h` 的觸發條件只來自反組譯，沒有執行。單次檢查的起始狀態是原始映像；常駐的 VM 記憶體在檢查後**不會重設**，所以同一次開機內的第二次檢查會從被改過的記憶體開始，這種情況沒有模擬。
- **公式是用測試驗證的，不是證明**：單元 04 能用 SMT 證明等價，這裡做不到，因為 RSSB 層有 50 萬條指令，而且裡面滿是依賴資料的分支。Gate 3 用的是 108 組密碼。`0x8000` 的搬移 bug 也可能藏在其他沒測到的路徑上。
- **輸入假設為可印 ASCII**（`0x20–0x7e`），長度最多 32，也就是 x86 會複製的上限。
- `RSSB_BASE`、`RSSB_HEAD`、`RSSB_IP0`、`TABLE`、`PROBE_Y` 這 5 個位址來自本節的分析，不是程式自動找出來的；任何一個寫錯，Gate 2 或 Gate 3 就會失敗。
- repo 裡原本的 `FlareOn/Fo5/12/solve.py` 只是印出寫死的 flag，`FlareOn/Fo5/writeup.md` 把檢查描述成「加總 + 位旋轉」，這和本單元還原的公式不符。
